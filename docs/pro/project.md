# Pro 项目说明

## 项目定位

**个人办公助手 Pro 主链路 Agent 的数据建设与后训练。**

Pro 接收用户即时发起的办公请求，例如查邮件、安排日程、修改文档、管理文件和处理演示文稿。任务常常需要多步工具调用，并依赖历史对话、具体对象和用户授权。

本人已确认独立负责数据合成与 LoRA SFT 全流程。个人贡献可以从以下三个方面讲述：

- 把业务中的行为问题转化为可训练的任务和质量标准。
- 把真实或合成执行轨迹转化为监督边界明确的多轮训练样本。
- 实现并调试长上下文 LoRA SFT，结合任务评测分析结果。

## 业务目标

| 能力 | 典型问题 | 希望模型学会的行为 |
|---|---|---|
| 工具选择 | 未找到正确工具、使用过期调用形式 | 根据实际工具空间搜索、加载和调用 |
| 对象与参数 | 文件、收件人、权限或编辑范围不明确 | 识别对象，传递有效且符合请求的参数 |
| 多步执行 | 只回复“会处理”，没有真正操作 | 完成工具动作，依据执行结果交付 |
| 授权判断 | 已授权仍反复确认，或未授权就执行高风险操作 | 根据具体授权范围和风险作出决定 |
| 长历史理解 | 混淆旧轮信息与当前请求 | 利用有效历史，明确当前任务边界 |

Pro 聊天链中的提醒创建工具与实际执行定时／事件提醒的 AutoTask Agent 是不同模块。当前介绍的主体是 Pro 主链路。

## 数据建设的出发点

### 真实轨迹需要先辨清来源和结构

线上 trace 包含 router、主 Agent、子 Agent、工具和平台处理过程。统计与训练前，要沿 parent 链识别哪些调用属于主 Agent，避免把路由转交或沙箱内部动作算成 Pro 的行为。

同一请求的上下文还可能包含初始化应答、早期历史召回和近期对话。这些信息与当前任务输出需要区别处理，不能把所有 assistant 角色消息都自动当作本次训练目标。

### 目标动作的覆盖不足需要定向补充

Notion 记录的一批五天、143,360 条经过质量筛选的主链候选中，命中指定 27 个评测领域工具的记录为 7,957 条，占 5.55%；该口径下若干目标写操作缺失。

这支持“分析目标能力缺口后补充任务”的方法。它不意味着所有线上办公行为都以读取为主：仓库的三天原始流量分析中，若干办公工具族写操作占比约 22%–36%。两个统计的时间窗口、过滤条件和工具范围不同。

## 本人的工作如何展开

1. **分析与定义。** 识别业务任务、工具覆盖、轨迹完整性和失败类型，明确需要补充的行为。
2. **构造与执行。** 清洗线上轨迹，基于已有可执行环境构造目标任务，执行多轮 Rollout。
3. **筛选与适配。** 检查环境、工具、输出协议及语义交付，筛选轨迹并准备训练格式。
4. **训练与调试。** 实现 LoRA 挂载、监督掩码、长上下文数据处理、打包和训练运行。
5. **结果分析。** 结合固定设置下的端到端评测，分析收益、退化和下一轮数据改进方向。

以上是本人负责的数据与训练工作。评测结果用于说明迭代过程，不据此延伸为独立建设整个产品或所有外部工具服务。

## 完整口头讲述

> 我独立负责 Pro 个人办公助手的数据建设和 LoRA SFT。项目主要优化多轮工具调用中的复杂操作、授权判断和任务完成能力。
>
> 数据侧，我先分析线上轨迹的任务分布和失败模式，明确哪些行为需要补齐。一方面清洗真实执行数据，另一方面复用可执行环境构造缺口任务，再通过 Rollout 和质量筛选获得训练轨迹。
>
> 我特别关注规则、环境和正确行为是否一致。例如，用户明确授权分享指定文件时，模型应该执行；如果只是讨论是否公开，还没有授权具体动作，则应该先确认。训练需要覆盖这些不同决策条件。
>
> 训练侧，我负责从轨迹转换到 LoRA SFT 的完整流程，包括当前任务边界、历史轮 loss mask、工具调用格式、LoRA 挂点及长上下文打包。模型应该学习的是当时可见信息下的动作，工具返回是上下文，不能被错误地当成输出目标。
>
> 最后结合办公任务评测分析收益和退化，并据此调整数据与训练配方。

## 如何体现技术深度

最值得展开的内容是：一次能力缺口判断、一个训练监督问题、一个实际失败定位。每个案例应回答“现象是什么、依据是什么、改了什么、怎样验证”。
