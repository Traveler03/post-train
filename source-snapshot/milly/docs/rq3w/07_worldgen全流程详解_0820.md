# 一、这件事要解决什么问题

## 1.1 背景

产品中有一项功能称为**Auto-task**: 用户自行编写一条规则,系统按时间或按事件持续监控。
例如"每天早上 9 点汇总当日会议与重要邮件",或"当邮件中点名要求本人审批时提醒"。

模型在该功能上存在两项长期缺陷:

1. **该说的没说全** —— 报告遗漏整个板块,或声明将创建草稿但未实际建立;
2. **不该说的乱说** —— 条件明显未满足,仍推送一条"已检查,一切正常",没有满足用户需求。

我们要用**训练**解决这两个缺陷。训练需要教材,教材需要题目。

## 1.2 为什么训练数据需要自己建设

线上有真实用户的轨迹,但**不能直接用作题目**,原因有两点:

- **存在真实用户数据** —— 其中包含真实的邮箱地址、日程与同事姓名;
- **不可重放** —— 当时用户收件箱中的邮件,轨迹里只保留了模型检索到的少数几条。
  我们无法让模型再执行一遍,因此没法判断它执行是否正确。

因此,我们设计的方案是:**将线上那次执行的轨迹作为剧本,重新构建一套隔离的工作环境,
让模型在该环境中重新执行同一任务。** 如果执行正确,这一遍的完整过程即构成一份训练教材。

## 1.3 名词解释

| 词 | 解释 |
|---|---|
| **规则** | 用户创建自动任务时输入的原始文本。我们**逐字保留、不做任何改写**,直接用作题目。<br>示例:"检查比特币(BTC)的实时价格。如果价格超过 $64,500,立即通知用户。如果价格未超过 $64,500,不要发送任何通知,静默跳过。" |
| **世界** | 为该题目构建的一套隔离工作环境:一个测试邮箱(7~8 封邮件)、一份日历(3~4 条日程)、一份通讯录、若干标签,必要时附一份表格。模型在其中执行任务,视其为用户的真实账号。<br>**等价表述:世界即该题目的考场环境。** 代码中称为"种子数据",因其是注入测试账号的初始内容。 |
| **该不该出声**<br>(代码中称"极性") | 该题目的**正确响应属于以下四类之一**:<br>**① 该报** —— 条件已满足,必须推送提醒;<br>**② 该憋着** —— 条件未满足,不得产生任何面向用户的输出;<br>**③ 正常交付** —— 日报周报一类,按格式输出内容;<br>**④ 如实说没事** —— 规则明确要求空窗时也需告知,则输出"本期无更新"。 |

⭐ **"该憋着"单独列为一类的原因**:它正对应 1.1 中的第 2 项缺陷。本批 2025 道题目中,
我们专门设置了 **485 道正确响应为"不产生任何输出"**的题目(占 24%)—— 模型多输出一句即判失败。

⭐ 以上述比特币这条case为例，对于同一条规则：

- 世界中放入"BTC 现价 $66,200" → 正确答案为**该报**;
- 世界中放入"BTC 现价 $62,800" → 正确答案为**该憋着**,且不得产生任何输出。

**因此,构建世界并非随机生成一批邮件,而是构造出一组内容,
使"该不该出声"的答案唯一确定、不存在第二种合理解释。**

# 二、合成Pipeline全景

```
线上真实记录
  │ ① 挑素材      筛出可用题目,定下本批造哪 1637 道         → 662 条规则 / 1637 道题
  │ ② 造世界      ⭐ 核心:由 Claude 为每道题构建工作环境    → 1637 份世界 JSON
  │ ③ 清洗 + 校验 检出并修复不安全或不合格的内容            → 校验报告
  │ ④ 装配        确定执行时刻、分配测试账号                → 题库文件 + 种子文件
  │ ⑤ 换标准答案  将标准答案改写为可判分的粒度              → 新题库
  │ ⑥ 渲染日期    将"明天""下周一"解析为绝对日期            → 无残留占位符
  │ ⑦ 上传        将题目与种子上传至评测平台                → 平台可见
  │ ⑧ 拒绝采样    发卷 + 三轮漏斗:错题才进下一轮            → 每题至多三次执行
  │ ⑨ 收割        仅保留判定通过的;第三轮另抠思考链         → 合格教材
  │ ⑩ 渲染        将教材转换为训练框架所需格式              → 训练数据
  ↓
进入训练
```

# 三、Query与用户种子数据(①)

本章对应全景图的第一步:**3.1~3.2 是从线上轨迹里筛出可用题目**,
**3.3~3.4 是定下本批造哪些题**(每条规则取多少道,并为每道题算一个指纹 ——
指纹用于事后确认"这道题是按哪一版配方造的")。

## 3.1 素材来源

| | |
|---|---|
| **输入** | 线上执行轨迹归档 `…/lsy/autotask/data/v3/v3_1/v3_1_balanced.jsonl.gz`<br>(**这是"v3.1"命名的来源** —— 批次命名为 v3.1.7 / v3.1.8,即因素材均出自该份 v3.1) |
| **脚本** | [`extract_source.py`](../../tools/autotask_pipeline/extract_source.py) —— [切分执行轨迹](../../tools/autotask_pipeline/extract_source.py#L232) · [提取规则原文](../../tools/autotask_pipeline/extract_source.py#L256) |
| **输出** | `source_pool.jsonl`(素材池)· `excluded_rules.jsonl`(剔除项及原因)· `arms_summary.json` |

**一条线上记录 = 某真实用户的某条自动任务在某日被触发的一次完整执行。** 其中包含:

- 用户编写的**规则原文**;
- 该次触发的**触发文本**(系统下发给模型的开场信息,含当前时刻与规则内容);
- 该次执行**调用了哪些工具、工具返回了什么**;
- 该次执行的**最终输出**;
- 当时**两名判官对该次执行的判定**。

⭐ **最后一项最为关键**:判官对"该报还是该憋着"的判定,**被我们直接采用为该题目的标准答案**。
因此本批题目的正确答案并非主观设定,而是线上真实发生、且经判官确认过的结果。

## 3.2 合成前的数据过滤

三道过滤都在 [`extract_source.py` 的主流程](../../tools/autotask_pipeline/extract_source.py#L398) 里,与评测集的重合度用 [8 字一组的 Jaccard](../../tools/autotask_pipeline/extract_source.py#L36) 计算。

| 过滤项 | 原因 | 剔除数量 |
|---|---|--:|
| **测试机器人记录** | 认证账号为 `testbeeai` 等内部测试账号,非真实用户 | **12 条** |
| **非标准记录** | 非"专业版"产品线,或触发格式非标准的定时/事件触发,或无实际触发 | **4 条** |
| **与评测集重合的题目** | **仅针对用户自行编写的规则**:与线上评测集题面高度重合(8 字一组的 Jaccard 重合度 ≥0.70)则整条剔除 | **0 条** |

> ⚠️ **该项过滤对官方模板豁免,且豁免属于主要情形。** 实测重合度 ≥0.70 的共 35 条规则,
> 其中数条**与评测题面逐字相同**,但它们**均为官方模板**(晨报 / 晚报 / 警报及其改版),无一被剔除。
> 依据是:评测集与线上使用的本就是同一份产品文案,**题面重合属于产品事实,不构成泄题** ——
> 隔离依靠世界内容完全不同,而非题面差异。
> 实际会被剔除的仅为用户自行编写的一次性规则,本批**无一命中**。

**过滤后剩余 2025 条可用记录,来自 1067 个不同的真实用户。**

## 3.3 Autotask的模板规则与用户种子数据合并

### 按**模板规则**合并(跨用户)

**合并键为规则原文本身。** 将原文小写化、归一化空白后计算 [SHA1 指纹](../../tools/autotask_pipeline/extract_source.py#L41)作为分组键 ——
**指纹相同即判定为同一条规则**,无论其来自多少个用户。

不同用户之所以会产生完全相同的规则,**原因在于产品提供了模板**:用户点击"晨报"即创建一条
自动任务,文案由产品预置、未经修改。因此大量用户共享同一条规则原文。

合并后每条规则下挂载 `records[]`,每条记录包含:执行用户(匿名键)、时区、触发时刻、完整执行过程。

| | |
|---|--:|
| 规则组数 | **662** |
| 执行记录总数 | **2025** |
| 涉及用户数 | **1067** |
| 仅有 1 条记录的规则 | **506 组(76%)** —— 绝大多数自定义规则仅由一名用户编写并执行过一次 |
| 最大的一组 | **208 条记录,来自 185 个用户** —— 葡萄牙语版"晨报"模板 |

⭐ **需要区分两个数量**:构建世界是**一条执行记录对应一个世界**,而非一条规则对应一个世界。
因此 **2025 是题目数**,662 表示这 2025 道题目中包含多少种不同的规则。

⭐ 但题目高度集中,所以设了上限，每个规则最多30条数据

| | |
|---|--:|
| 最大的 **1** 条规则(葡语晨报模板) | **208 道题 = 10.3%** |
| 最大的 5 条 / 20 条 | 22.9% / **47.5%** |
| 仅出现 1 次的 506 条规则 | 合计仅占 25.0% |

这些题目的**世界内容各不相同**(并非重复数据),但**题面文本完全一致** ——
成本与梯度集中消耗在少数几条官方模板上,而**多样性最高、难度最大的自定义规则仅占四分之一**。

⇒ **每条规则最多取 30 道**([`--max-per-rule 30`](../../tools/autotask_pipeline/gen_worlds.py#L1063))。14 条规则超限、共削减 388 道,
题目数 **2025 → 1637**,按当前 $0.615/个计算**节省约 $239**;
**自定义规则未受影响**(其中记录数最多的也不足 30 条)。

⚠️ 落在上限之外、但**之前已经造好**的稿件不会被自动删除 —— 装配步骤按目录扫描,
放着不管它们照样会进最终数据集。本批已把这类稿件移出到 `cases_out_of_cap/`,
**最终规模即 1637 道**。

### 按**用户**合并种子数据(跨记录)

**脚本** [`build_user_mailboxes.py`](../../tools/autotask_pipeline/build_user_mailboxes.py),产物 `user_mailboxes_caldrive_0820.jsonl`。
三类观测各自的采集范围与字段:[邮箱](../../tools/autotask_pipeline/build_user_mailboxes.py#L33) · [日历](../../tools/autotask_pipeline/build_user_mailboxes.py#L223) · [网盘](../../tools/autotask_pipeline/build_user_mailboxes.py#L299);多层截断 JSON 的解析见 [`peel()`](../../tools/autotask_pipeline/build_user_mailboxes.py#L110)。
拼进提示词的三段参照:[邮箱](../../tools/autotask_pipeline/gen_worlds.py#L238) · [日历](../../tools/autotask_pipeline/gen_worlds.py#L282) · [网盘](../../tools/autotask_pipeline/gen_worlds.py#L357)。

线上轨迹中,模型每次执行都会检索邮件、查询日历、读取表格,工具**确实返回过**一批真实内容。
将同一用户散布在各条记录中的这些片段按用户聚合,即可得到**该用户账号的大致形态**。
构建其世界时以此为参照,生成的环境更贴近该用户的真实情况。

⛔⛔ **需要特别澄清:该数据仅进入提示词,不会进入世界。**
世界中的内容**全部由模型生成**(见 4.1)。

**规模**:

| | 邮箱 | 日历 | 网盘/表格 |
|---|--:|--:|--:|
| 扫描的工具返回次数 | 8,774 | 1,697 | 1,346 |
| 其中返回为空 / 截断至不可解析 | — | **1,215 条为空(71.6%)** + 269 条截断 | 631 |
| 聚合出的去重条目数 | **12,329 封邮件** | **206 条日程** | **172 个文件** |
| 覆盖用户数 | 1,067 | **64** | **85** |
| 构建世界时**实际获得参照**的题目 | **635 / 2025 = 31.4%** | **169 / 2025 = 8.3%** | **273 / 2025 = 13.5%** |

⚠️ **日历数据较为稀疏**:39% 的记录调用过日历工具,但**七成以上的调用返回为空日历**
(查询按天发起,该用户当天确无安排),再扣除截断部分,最终仅 8.3% 的题目能获得参照。
补充该项的理由不在覆盖率,而在于此前该项为零,且它同时提供了一份可用于核对形态目标的地面真值。

### 为什么只合并这三类数据

因为**只有这三类属于"账号内长期存在、具备稳定 ID"的内容**,跨记录合并才有意义:

- **天气 / 行情 / 联网搜索 / 新闻** —— 属于一次性查询结果,不是账号内容,合并无意义;
- **记忆(memory)** —— **无需也无法单独注入**。平台会**从种子的邮件与日历自动建立索引**
  (注入种子时会等待其进入向量库)。因此邮件与日历注入正确,记忆即随之正确。
  ⚠️ 反之亦然:**未能进入索引的内容模型无法看到** —— 7.2 中"日程一律排在未来"这一条即由此而来。

## 3.4 规则的五个家族

依据规则原文的起始句或标志短语识别([`classify_arm()`](../../tools/autotask_pipeline/extract_source.py#L88),每种语言的官方模板各一套),划分为五类,
用于统计与抽样分层,同时便于定位哪一类题目模型失败率最高。

| 家族 | 说明 | 规则组数 | 执行记录数 |
|---|---|--:|--:|
| `custom` | 用户自行编写,形态多样 | 497 | 924 |
| `template_variant` | 官方模板的改版,或其它官方技能(未读邮件处理、会议材料汇总、订阅续费监控等) | 90 | 587 |
| `template_dawn` | 官方**晨报**模板原文 | 4 | 265 |
| `template_evening` | 官方**晚报**模板原文 | 5 | 183 |
| `alert` | 官方**重要邮件警报**模板 | 66 | 66 |

**四条真实规则示例**(取自素材池):

```
① 定时 / 英文 / custom
   Use daily-brief Skill: Start with a brief greeting and today's weather, then summarize
   my day ahead: key meetings and calendar events (who's attending, what to prepare), and
   any important unread or unreplied emails from the past 24 hours. Keep it brief and actionable.

② 定时 / 中文 / custom
   检查比特币(BTC)的实时价格。如果价格超过 $64,500,立即通知用户。
   如果价格未超过 $64,500,不要发送任何通知,静默跳过。

③ 定时 / 葡语 / custom
   Todos os dias às 9h, busque na web a previsão diária do horóscopo de Touro (♉) …

④ 事件 / 印尼语 / alert(官方警报模板)
   Pemicu: Email yang dikirim langsung ke saya (di kolom Kepada, bukan hanya CC/BCC) …
   (触发条件:直接发送至本人"收件人"栏的邮件,仅抄送不计)
```




# 四、构建世界(②)

| | |
|---|---|
| **输入** | 题目身份(规则原文 + 该不该出声 + 语种 + 时区)+ 材料(见 4.4) |
| **模型** | `claude-opus-5`,temperature 0.7,单次输出上限 24,000 词元 |
| **输出** | 一份 JSON:`world_story`(内部说明)/ `seed`(世界本体)/ `trigger_event`(事件题的触发详情)/ `expected_output`(标准答案)/ `polarity` |

## 4.1 一个"世界"最终包含什么

模型对每道题输出一份 JSON,其中 `seed` 即注入测试账号的世界本体。
第三列是**这一项在多少比例的世界里非空**:100% = 每个世界都有,33.6% = 只有约三分之一的世界带网盘文件。

| 字段 | 内容 | 有多少世界带这一项 | 形态要求 |
|---|---|--:|---|
| `emails` | 收件箱。每封含发件人/收件人/抄送/主题/正文(HTML)/附件/时间偏移/未读/重要标记 | **100%** | 共 7~8 封:A 档 3 封长邮件(2000~4000 字符)+ B 档 4~5 封短邮件(500~1000 字符) |
| `calendar_events` | 日历。每条含标题/起止/参会者及其回复状态/组织者/地点/说明/是否全天 | **100%** | ≤4 条;约半数为周期会议的独立实例;**不得排在过去** |
| `contacts` | 通讯录 | **100%** | 含 id 与姓名字段 |
| `labels` | 用户自建的邮件标签 | 72.5% | 至多 1~2 封邮件带标签 |
| `drive_files` | 网盘文件与表格内容 | 33.6% | 仅当该题当年真调过网盘/表格工具时提供;1 份文件、表格 20~40 行 × 8~12 列 |
| `user_notes` | 用户存过的长期偏好 | 4.3% | 多数题目不提供 |

同一份 JSON 里还有四项**不进入世界、供评测与核查使用**的字段:

| 字段 | 用途 |
|---|---|
| `expected_output` | **标准答案**。三段:考察点(`goal`)、判定依据(`describe`)、硬性判分点(`key_constraints`) |
| `polarity` | 该题的正确响应类型(该报 / 该憋着 / 正常交付 / 如实说没事) |
| `trigger_event` | 事件题的触发详情(邮件触发与日历触发字段不同);定时题为空 |
| `world_story` | 一段内部说明:这个世界是怎么回事、为什么该响应类型成立。**不下发给被测模型** |

⛔ **世界中的全部内容均由模型生成**,`seed` 里没有任何一行由代码从线上材料直接复制。
线上轨迹与同用户参照仅进入提示词,作为重建依据与形态参照。

## 4.2 系统提示词:11 条硬约束

我们对原始世界数据使用prompt进行改写，并在训练中只使用改写后的数据，以防出现敏感信息被训练的情况。

[系统提示词](../../tools/autotask_pipeline/gen_worlds.py#L712) 共 10,013 字符 = **11 条硬约束 + 9 条形态条款 + 输出格式模板**。首句为:

> 你在为"自动任务提醒助手"的数据工厂造可运行的题:给定一条真实用户的自动任务规则(原文,不许改),
> 你要设计一个全新的账号世界(种子数据,会被注入测试 Gmail 账号),让这条规则在这个世界里
> **可以被执行、且正确行为无歧义**。

**11 条硬约束(违反即判废)**,下表为逐条说明:

| # | 约束名 | 说明 |
|---|---|---|
| 1 | 实体一致性优先 | **规则中点名的实体必须在世界中真实存在且名称完全一致。** 若规则要求"Dhika 回复的邮件保持未读",世界中就必须存在名为 Dhika 的人 —— 改名等同于破坏判定条件。<br>邮箱地址须替换为安全域 `@mock.test`,且**地址部分必须为纯 ASCII**(人名可保留重音符号,地址不可,否则注入环节整题失败)。**规则未点名的人物一律重新虚构。** |
| 2 | 时间全部相对 | **禁止写入绝对日期。** 邮件时间以"相对执行时刻的天/小时偏移"表示,正文中需要提及日期时使用占位符(第 ⑥ 步再解析为绝对日期)。否则该批题目两周后即失效。 |
| 3 | 日历偏移写法 | "今天/若干小时后"使用分钟偏移;"明天/后天"使用天偏移 + 具体时刻。 |
| 4 | **极性可判** | **答案必须唯一。** 仅依据世界内容即可唯一确定该不该出声,不得存在两种合理解释。<br>"该憋着"类题目的难点在于:触发邮件须做到**"表面符合触发条件,细读规则却明确不达标"** —— 例如仅抄送而非直接发送、属常规审批、措辞紧急但实无风险、纯营销内容。模型必须真正理解规则才能保持静默。 |
| 5 | 真实感 | 收件箱须包含噪声(促销、订阅、系统通知、抄送线程),关键信号需**混杂于噪声之中**。**A 档 3 封长邮件 + B 档 4~5 封短邮件,共 7~8 封**(数量与长度见 4.1)。 |
| 6 | 语言 | 世界语言与该用户语言一致;标准答案三个字段同样如此。 |
| 7 | 纳入项与排除项须成对出现 | 规则中凡包含筛选条件的(时间窗、是否已处理、是否本人负责、收件人还是抄送、是否熟识),世界中**必须同时存在"达标项"与至少一个"高度相似但不达标的干扰项"**。否则模型全选亦可通过,题目失去区分度。 |
| 8 | 动作必须落地 | 规则要求创建草稿、标记已读、删除、发送、更新表格的,**标准答案必须要求真实完成对应工具调用**。仅给出建议文案或声明"将会处理"—— **判为失败**。 |
| 9 | 报告须完整 | 规则要求多个板块/字段/时间段的,世界中**每一项都须有对应证据**,并**刻意保留一项容易遗漏、且确实尚未解决的事项**。"标题正确但缺少段落"不予通过。 |
| 10 | 证据闭环 | 任何数字、时间、人物关系、处理状态,**均须能在世界中找到出处**。信息不足时写"未知/缺数据",**严禁为使答案完整而虚构**。 |
| 11 | 两类空输出须严格区分 | **该憋着** = 面向用户的内容为空、信封标记为不通过,**且不得解释未提醒的原因**;**如实说没事** = 规则明确要求空窗时也须报告,则内容非空、信封标记为通过。两者不得互换。 |

## 4.5 完整示例

以本批中一道印尼语**警报**题目为例:

**规则原文(节选,官方警报模板)**:"触发条件:直接发送至本人'收件人'栏的邮件(仅抄送/密送不计)。
仅当该邮件确属重要、需立即处理时触发……"

**线上真实结果**:**该憋着**。

**模型构建的世界**:

- **内部说明**(供内部核查,不下发给模型):"Nadira 是某零售企业的行政专员。触发邮件由同事
  Bagas 发送至外部物业管理方的三个地址,Nadira **仅在抄送栏**。规则首句要求必须直接发送至
  收件人栏方可触发,且明确排除'仅抄送的知会线程',因此必须保持静默。**对照项**:一封三天前
  确实发送至收件人栏的紧急升级邮件已处理并已提醒;另一条合同报价线程属常规低风险审批。"
- **收件箱 9 封邮件**,触发邮件主题为 `[URGENT] 2 号电梯与大堂闸机故障 – 请今日处理`,
  收件人为三个外部物业地址,本人**仅在抄送栏**。正文为一封形态真实的故障报修函。
- **日历 4 条**,例如"行政管理周同步会",次日 9:30–10:00,含组织者、参会者及各自回复状态。
- **通讯录 5 人 · 标签 2 个 · 网盘文件 0 个**。
- **标准答案**:
  - *考察点*:"考察模型是否检查收件人字段:触发邮件中本人仅在抄送栏,规则要求必须在收件人栏,
    正确终态为**完全静默、不产生输出**。"
  - *硬性判分点*:"内容必须为空且信封标记为不通过;**不得输出任何面向用户的提醒,
    亦不得解释未提醒的原因**。"

⭐ 该题目的设计要点在于:**仅凭"识别到 `[URGENT]` 即告警"必然出错**。模型必须实际检查收件人字段,
并排除另外两封高度相似的干扰项。这是硬约束 4 与 7 在单道题目上的具体落地。

|---|---|---|
| 1 | 一轮**新增覆盖 < 5%** | 继续投入的边际收益已经很低 |
| 2 | 一道题**连续 4 轮未通过** | 不再追。多为**题目本身有问题**(标准答案写歪或存在歧义),硬逼出来的那次通过反而是脏数据。这些题落入 `hard_questions.txt` 交人工复核 |
| 3 | 走完三轮 | R3 之后不再加轮次:同一道题第四次重跑的边际收益,已经低于把预算花在新题上 |
| 4 | **任何一道校验未通过** | 立刻停止,不再提交 |

### 判"做对了"要两条独立通道同时成立

只依据平台的判定字段是不够的 —— 它出现过判官输出被截断、模型输出被拼接污染等情况。
因此要求:

- **通道①** 平台判定为通过;
- **通道②** 该次执行的 live trace 末轮正文是**可解析的信封**(`content` / `reason` / `pass` 三项齐全)。

**两条都成立才计为通过。** 只满足①的标记为 `suspect`,**既不计入覆盖率、也不进入教材**,
单独落盘供复查。

### 收割产出(⑨)

[`harvest_select.py`](../../tools/autotask_pipeline/harvest_select.py) 按题目聚合(合并同题的多次执行),输出四份:

| 产物 | 内容 |
|---|---|
| `sft_pass.jsonl` | 每道题通过的那次执行轨迹。同题多次通过时取分数最高的一条(同分时的选择与线程顺序无关,保证可复现) |
| `dpo_pairs.jsonl` | 既有通过又有失败的题目,配成「最好的通过 × 最差的失败」偏好对 |
| `allfail_questions.txt` | 全部失败的题目 |
| `coverage.md` | 按家族统计的覆盖率与收成 |

### 收割侧的三条判据

- **`low_confidence` 按同批中位数相对判定**,而非固定阈值 —— 该字段是收割时刻的瞬时值,
  固定阈值会随轮次策略变化而失效;
- **按提交台账原文核对档位**,确保低档题目不会选中高档执行结果作为教材;
- **审计中的内存标记不作为筛选依据** —— 实测有无该标记时,通过率、调用数、长度三项完全一致。

### 上一批的实际收成(两轮口径)

```
2025 道题目 → 拒绝采样 → 判定通过 1443 条 → 渲染保留 1281 个任务 → 1281 条训练样本
```

⚠️ 这是 **v3.1.7** 的数字,是**带日期的快照**不是常量 —— 轮次策略、分数闸、
题库规模一变就全变(v3.1.8 分层闸口径是 974 题)。引用前先自己算。

## 5.6 渲染为训练数据(⑩)

[`render_sft.py`](../../tools/autotask_pipeline/render_sft.py) → [`prepare_dsv4_data.py`](../../training/scripts/dsv4/prepare_dsv4_data.py):
将通过的执行轨迹整条渲染为训练样本,以多段掩码标注需要学习的部分。

**⭐ 0821 补:这一步的实际命令行**(原文只有一句话,没有参数 —— 而每个参数都能
静默毁掉一整批数据。编排脚本正本在 `data/autotask_rq3w/<版本>/chain_harvest.sh`,
0821 起已入 git)。

```bash
# ⑩-a 渲染:轨迹 → SFT 样本
python3 tools/autotask_pipeline/render_sft.py \
  --sft   <版本>/full/harvest_merged/sft_pass.jsonl \
  --out   <版本>/full/sft_samples_merged.jsonl \
  --min-score 5 --relax-score 4 --relax-when-constraints-ge 4 \
  --items <版本>/full/<主批>_items.jsonl,<版本>/dawnfix/dawnfix_items.jsonl \
  --keep-low-confidence --allow-raw-pii

# ⑩-b 打包:SFT 样本 → 训练数据(顺便拿长度分布定 SEQ_LEN / TRAIN_ITERS)
python3 training/scripts/dsv4/prepare_dsv4_data.py \
  --src <版本>/full/sft_samples_merged.jsonl \
  --model models/DeepSeek-V4-Flash-0731 \
  --out-dir <仓库外>/dsv4_run/data_<批次>_<时间戳> \
  --render whole --thinking-mode thinking \
  --reasoning-effort source --max-len 98304 --src-format openai
```

**每个参数为什么是这个值:**

| 参数 | 为什么 |
|---|---|
| `--render whole` | 整条轨迹渲一条 + 多段掩码。和逐轮「爆破」**梯度逐 token 相同**(前缀是严格前缀、掩码位置重合、loss 按全局 token 归一),但爆破把同一份前缀重复编码约 5 遍 ⇒ 省 4.19 倍算力。**没有默认值,必须显式给**;`explode` 只为复现旧实验 |
| `--min-score 5` + `--relax-*` | **分层分数闸**。一刀切卡 5 分会系统性剔掉多交付题(0821 实测:被剔的 152 条里 84.9% 是 ≥4 条约束的题),而「漏做」是官方卷第一大失败。分层后 974 题 / 58.3% 多交付题,一刀切是 845 / 52.0% |
| `--items` | 分层要读 `key_constraints` 条数,**主批和补题批都要给**。对不上号 >10% 会直接退出(fail-closed) |
| `--keep-low-confidence` | `low_confidence = 判定数 < 2`,是收割那一刻的**瞬时值**。以后每题只跑一轮 ⇒ 判定数恒为 1 ⇒ 不给这个开关会把样本**全部剔光** |
| `--allow-raw-pii` | 本批政策是**不脱敏**(真实性就是价值)。不给这个也不给 `--pii-traces` 会拒绝渲染 —— 这道闸拦的是「没人查过」,不是「一定有」 |
| `--reasoning-effort source` | 按轨迹自己的档位写 prompt 前缀。⚠️ 前提是教材**全是 low 档**;混了高档必须改用固定值 |
| `--max-len 98304` | 先不设限,拿到完整长度分布再定 `SEQ_LEN`。定小了会**静默丢样本** |

⛔ **两个会静默出错的地方**(都踩过):
- `sft_pass.jsonl` 原来**不写 `score` 字段**,而分数闸把「取不到分数」当作不合格 ⇒
  `--min-score 5` 会剔光 100% 的行、渲出 0 条,日志一切正常。0821 已修
  (收割器补写 `score`,渲染端加 `assert_score_gate_can_fire()`);
- **闸的验收标准是「在真路径上会响」,不是「写了」。** 上面那个 bug 是有契约测试的 ——
  测试喂的是手搓的行(带 score)。验法:拿 `git show HEAD:<file>` 的修复前版本跑一遍新测试。
