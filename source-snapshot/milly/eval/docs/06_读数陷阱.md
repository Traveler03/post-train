## 一、失败率:最容易毁掉整个结论的东西

**症状**:一卷 112 题,拉下来发现几十道题的 `actual_outcome` 是空的。

**为什么致命**:跑挂的多是**长题、难题**(多轮、工具调用多),活下来的都是短题。
所以剩下那些题算出来的分**系统性虚高**。实测:

| 判官判完的 run(≥100 题) | 判到一半的 run(46~58 题) |
|---|---|
| 51.4 / 44.8 / 53.4 / 27.5 / 31.2 | 81.2 / 70.6 / 68.8 / 67.4 / 73.5 |

**没有一个例外,差约 20 分。**

**怎么办**:每次出分先跑
```bash
python3 scripts/short_runs.py
```
**失败率 > 10% 的 run 直接作废重跑**,别心疼。

**注意区分两种"没判分"**:
- 推理失败(`actual_outcome` 是空的)→ 这卷废了,重跑
- 判官还没跑完(有答案没分数)→ 等一等重拉就有了

## 二、单轮结果不能下结论

同一个模型、同一卷题、什么都不改,重复跑的实测差距:

| 什么 | 两轮之间差 |
|---|---|
| 底座(4 轮) | 标准差 3.3 分 |
| 某个 LoRA 档 | 6.6 分 |
| 另一个档 | **13.8 分** |
| 又一个档 | **22.6 分**(66.7 → 44.1) |

**推论**:两个实验差 5 分,基本读不出区别。
我们出过一次乌龙:单轮读到 **+19.2 分**,补到 3 轮变成 **+7.7 分**,
最高那轮就是运气好。

**规矩**:关键结论至少 3 轮,而且要报每一轮的值,不只报均值。

## 三、⛔⛔ 训练随机种子的方差,比"哪版数据更好"还大

这条是最反直觉的。

同一份数据、同一套配方,**只换训练随机种子**重跑一遍:
- 整条曲线差 **2.2 分**
- 单个档最高差 **11.8 分**

而我们六个不同数据版本之间的全距只有 **4.1 分**。

**意思是:"哪版教材好"这个排序,被种子噪声整个盖过去了。**
单种子实验读不出数据版本的差别。要检出 3 分的差距,每个臂需要 4 个种子。

**与其把一个实验跑 20 轮评测,不如跑 2 个训练种子。**

## 四、思考档位换了 = 尺子换了

同一个底座:

| 档位 | 分 |
|---|--:|
| `no_think` | 48.4%(4 轮) |
| `low` | 63.7%(2 轮) |
| `high` | 60.1%(3 轮) |

**光开思考就 +12.9 分,超过我们所有训练效果之和。**

而且开了思考之后,**所有 LoRA 档从"赢底座"翻成"输底座"**(−6.5 ~ −26.9)。
故障率也从 2/93 涨到 28~61/93(模型思考不收尾,把额度烧光交白卷)。

**规矩**:不同档位的分数**绝对不能画在同一条曲线上**。发任务时 `被测模型` 字段
(`ais-relay-no-think` / `-low` / `-high`)决定档位,记在实验名里。

## 五、⛔ 本节原来的结论已经完全反了(0817 更正)

> **原文写的是**:「`liveish` 环境实测三次全废……**一律用 `test`**」。

被测模型写成字符串而不是 dict,平台静默用默认模型代答(详见 13 号文的
「静默换模型」和「live 环境三小时排障实录」)。修好之后 liveish 一直是主力。

现在真正要防的三条:

| 要防的 | 判据 |

## 六、"档没挂上"和"通道被占"会产出看起来正常的假分数

这是最阴的一类,因为**平台一切正常,分数照出**。

**情况 A:LoRA 档没挂上。**
评测跑的是裸底座,你以为是微调后的效果。
→ 脚本里已经加了硬闸:挂不上**直接退出不发任务**。别绕过它。

**情况 B:PFB 通道被别人的 worker 占着。**
你的 worker 日志刷 `409 Conflict`,但平台把流量发给了**占着通道的那台机器**。
实测出过一次:平台显示跑了 170/112,答题的是另一台机器上的另一个模型。
→ 发任务前必查:
```bash
tail -3 ~/.ais-relay-<你的TAG>/worker.log      # 有 409 就换通道
```

**情况 C:换档打断了在飞的题。**
平台的完成计数**严重滞后**(实测 51/112 时平台就说跑完了)。
如果队列脚本这时换下一个档、重启 worker,**那一瞬间所有在飞的连接一起断**。
实测抽 24 道失败题,全部死在**同一秒**。
→ 一条队列一次只放一个档。

## 七、判定要按题重采样,不是按 run 算 p 值

我们出过一次:某个档 run-level 的 p 值算出来 0.0002(看起来极显著),
但**按题重采样**的置信区间是 [−2.9, +10.0] —— **含 0,根本没立住**。

原因:run-level 检验假设每个 run 是独立样本,但题与题之间的难度差异才是主要方差来源。

**规矩**:报结论要给按题重采样的置信区间,不要报 run-level p 值。

## 八、镜像卷只能当烟测,不能排名

我们有一套本地复刻的评测卷(镜像卷)。实测:
- 47 题逐字重合、同档同题
- 镜像卷 30.1% vs 线上 44.2%
- **逐题相关性只有 r=0.23**

**所以镜像卷只能用来看"行为指纹"(比如信封格式对不对、有没有打转),
不能用它的分数给模型排名。**

## 九、别用 `pkill -f`

`pkill -f` / `pgrep -f` 会匹配**命令行里带该字面量的任何进程,包括你自己**。
我们踩过三次:自杀两次 + 死循环 39 分钟。

统一用:
```bash
python3 scripts/kill_by_name.py <进程名片段>
```
它按 `/proc/<pid>/comm` 判定,不看命令行。

⚠️ 但它**杀不掉 vLLM** —— vLLM 的进程名是 `VLLM::EngineCore` 之类,不含 "vllm"。
vLLM 只能按 PID 杀 —— 停服务/停 worker **一律走 `eval/scripts/svc_kill.sh`**
(特征串经文件传、shell 豁免、支持 `--dry`),严禁 `pkill -f` 按名字匹配。

## 十、平台任务接口只返回"在跑"的

跑完就整条消失,**查不到"完成"或"失败"的终态**,而且 `completed_cases` 计数严重滞后。

**所以"列表里查不到" ≠ "跑完了"**,还可能是:
- 任务刚发出去、还是 pending 没进 running 列表
- 接口超时(平台是单机小水管,偶发超时)

判"这一档跑完没有",老写法是**同时满足**:
① 曾经在平台上见过它 ② 现在列表里没有了 ③ 最近 15 分钟没有新请求落盘
(原文提到的 `scripts/pfb_queue.sh` 已不存在;现在的实现是 `eval/scripts/deck_watch.sh`,
它是**唯一合法的等卷原语**,规矩是「见过之后连续两次空列表才判离场」。)

**⛔ 0817 补:上面这套只解决了"别误判成跑完了",没解决反过来那一半。**
一张**已经收官**的卷查出来也是「没有匹配的任务」,和「压根还没发出去」完全同形。
所以按"先等它出现"写的脚本,碰到已收官的卷会**干等最多 3 小时**
(当天白等 15 分钟;`deck_watch.sh` 同样盲,盯已收官的卷会空转到超时)。

正解是另外查一条**含已收官卷**的登记表:

```bash
python3 eval/scripts/pull_run_complete.py --list-runs --dataset '<主卷或官方卷>' | grep '^<卷名>'
```

三路分流(已落进 `data/autotask_rq3w/v7_20260812/pull_runs.sh`):

```
live       在跑              → 交给 deck_watch.sh 等离场
registered 登记过但不在跑     → 已收官,直接放行,不等
两个都不是                   → 真的还没发出来,才需要等
```

⚠️ 别用「档案文件在不在」当唯一判据 —— 档案只有拉了才有,拉又被这个循环挡着,是死循环。
